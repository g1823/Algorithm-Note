# 石子游戏 VII [1690]

## 1. 解题思路

**问题**：`stones[i]` 表示第 i 颗石子的价值，排成一行。Alice 先手，每轮从**两端任取一颗**，**本轮得分 = 取完后剩余所有石子的总和**（不是取的那颗的值）。无石可移除时得分高者胜。Bob 尽力缩小分差，Alice 尽力扩大分差。返回**得分差值**。

**核心难点**：得分规则特殊（"剩余总和"而非"所取的值"），但博弈框架不变。

**核心洞察**：

1. **得分是"剩余总和"**：越早取，剩余越多，单轮得分越高；但取完剩下的区间还得给对手玩——这是典型的"本轮收益 − 对手后续优势"的**零和博弈**结构，和系列前几题同构。
2. **动作是两端取**：剩余永远是**连续子区间** `[l, r]` → 区间 DP，状态 `dp[l][r]`。

**状态定义**：

- `dp[l][r]` = 区间 `[l, r]` 剩余时，**当前玩家**相对对手的净胜分（Alice 视角）
- `dp[i][i] = 0`：只剩一堆，取走它后剩余总和为 0，双方净差 0

**转移**（前缀和 O(1) 求区间和）：

```
sum(l,r) = prefixSum[r+1] - prefixSum[l]

取左边 l：本轮得分 = sum(l+1,r)（拿走 l 后的剩余总和）
         → 净胜 = sum(l+1,r) - dp[l+1][r]
取右边 r：本轮得分 = sum(l,r-1)
         → 净胜 = sum(l,r-1) - dp[l][r-1]

dp[l][r] = max(取左的净胜, 取右的净胜)
```

**填表顺序**：`dp[l+1][r]`、`dp[l][r-1]` 都是**更短区间** → 按区间长度从小到大填（区间 DP 通用套路，同 1563）。

**答案**：`dp[0][n-1]`（Alice 先手，站在当前玩家视角即为 Alice 的净胜分）。

## 2. 代码实现

```java
package leetCode.moderately;

/**
 * @description: 1690. 石子游戏 VII
 *
 * 思路：零和博弈（博弈DP，区间型）。得分逻辑特殊：每轮从两端取一颗石头，
 * 本轮得分 = 取完后剩余所有石子的总和（而非取的那颗的值）。
 * 剩余局面永远是连续子区间 [l, r]，用区间 DP：dp[l][r] = 当前玩家在 [l,r] 上的净胜分。
 * 复杂度：时间 O(n²)，空间 O(n²)，n ≤ 1000。
 */
public class StoneGameVII {

    /**
     * 博弈DP：返回 Alice 相对 Bob 的最大净胜分（得分差值）
     *
     * 状态定义：dp[l][r] = 区间 [l, r] 剩余时，当前玩家相对对手的净胜分。
     * 边界：dp[i][i] = 0（只剩一堆，取走它后剩余总和为 0，双方净差 0）。
     * 转移：设 sum(l,r) 为区间总和（前缀和 O(1) 求），当前玩家从两端二选一：
     *   取左边 l：本轮得分 = sum(l+1,r)，对手在 [l+1,r] 的净胜 = dp[l+1][r]
     *            → 净胜 = sum(l+1,r) - dp[l+1][r]
     *   取右边 r：本轮得分 = sum(l,r-1)，净胜 = sum(l,r-1) - dp[l][r-1]
     *   dp[l][r] = max(两者)（当前玩家取对自己最有利的一边）
     * 填表：dp[l+1][r]、dp[l][r-1] 都是更短区间，按长度从小到大填。
     * 答案：dp[0][n-1]（Alice 先手，站在当前玩家视角即为 Alice 的净胜分）。
     *
     * @param stones 每颗石子的价值
     * @return Alice 相对 Bob 的最大得分差值
     */
    public int stoneGameVII(int[] stones) {
        int n = stones.length;
        // 前缀和-快速求区间和
        int[] prefixSum = new int[n + 1];
        for (int i = 0; i < n; i++) {
            prefixSum[i + 1] = prefixSum[i] + stones[i];
        }
        // 默认dp[i][i] = 0：单独1堆石子，取走它剩余0，总得分0，双方净差0
        int[][] dp = new int[n][n];
        // 按长度填表，确保小区间先填充（只填右上角 r>=l 的区域，区间 DP 只有这个区域有意义）
        for (int len = 2; len <= n; len++) {
            for (int i = 0; i + len - 1 < n; i++) {
                int l = i, r = i + len - 1;
                dp[l][r] = Math.max(
                        prefixSum[r + 1] - prefixSum[l + 1] - dp[l + 1][r],  // 取左边
                        prefixSum[r] - prefixSum[l] - dp[l][r - 1]           // 取右边
                );
            }
        }
        return dp[0][n - 1];
    }
}
```

## 3. 踩坑记录

- **验证示例记错**（本次真实发生的坑）：最初用 `[5,3,4,5]→3`、`[7,7,7,7,7,7,7]→28` 验证，代码输出 9/21 对不上，误以为代码有 bug。实际官方示例是 `[5,3,1,4,2]→6`、`[7,90,5,1,100,10,10,2]→122`，代码全部通过。**教训：验证用例必须来自题目原文，不能用记忆/猜测的示例。**
- **得分理解**：容易把"本轮得分 = 剩余总和"误解为"取的那颗的值"。注意区分：越早取单轮分越高，这是本题得分规则的核心特征。
- **净胜分视角**：`dp[l][r]` 是"当前玩家 vs 对手"的净胜分，取左边时本轮得分是 `sum(l+1,r)`（剩余区间），不是 `sum(l,r)`（不能把已取的石子算进本轮得分）。

## 4. 技巧总结

- **"得分逻辑变、博弈框架不变"**：哪怕得分变成"剩余总和"这种反直觉规则，只要仍是双人轮流 + 净胜分对比，转移永远是 `本轮收益 − 对手后续净胜`。先识别零和结构，再套用状态维度（本题两端取 → 区间 DP）。
- **区间 DP 通用模板**（同 1563）：`for len = 2..n { for i = 0..n-len { r = i+len-1; 枚举取法; dp[i][r] = max(...) } }`。
- **取走端点 = 得分用"剩下的区间和"**：`sum(l,r) − stones[l] = sum(l+1,r)`，可直接用前缀和表达，语义清晰。
- 与系列其他题对比：877（两端取整堆，奇偶分组 O(1)）、486（两端取数，同样净胜分区间 DP）、1690（两端取一颗，得分=剩余总和）——**同一"两端取"动作形态，得分规则不同导致状态定义相同但转移细节不同**，是理解"动作形态 vs 得分规则"两维度的好素材。
- 相关经典解法：[博弈DP(零和博弈)](../经典解法/动态规划DP/博弈DP(零和博弈).md) 6.2.7 节。

## 5. 思考过程

本次学习基于与 agent 的对话完成：

1. **规则理解**：一开始对"得分 = 剩余总和"感到困惑，用一句话确认后立刻意识到"还是零和博弈，只是得分逻辑转换为剩余总和"——识别出博弈框架没变，这是本系列学下来的"肌肉记忆"。
2. **边界确认**：`dp[i][i]=0` 的推导很顺畅（取走唯一一堆，剩余 0，得分 0，双方净差 0），没踩坑。
3. **最大的坑在验证环节**：代码一次写对，但 agent 给的验证示例是记错的，导致"代码明明对却对不上"。通过查官方题目原文才发现示例错误。这个教训反而不是算法层面的，而是工程层面的：**用例必须来自权威来源**。
4. **认知总结**：整个石子游戏系列（877→1690）学下来，核心收获不是某个 DP 模板，而是——**先判断博弈类型（零和/单人最优化/必胜态），再定状态维度（区间/下标/参数/剩余数），最后套"收益 − 对手优势"或"存在一步令对手必败"的转移**。这套识别流程已经内化。
