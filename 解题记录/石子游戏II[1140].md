# 石子游戏 II [1140]

## 1. 解题思路

**问题**：若干堆石子排成一行 `piles[i]`（正整数），Alice 先手，两人轮流**从前端**取 `1~2M` 堆，取后 `M = max(M, 本次取堆数)`，初始 `M = 1`。取完全部堆后，总石子数多者胜。求 Alice 最多能拿到多少颗石子。

**核心难点**：与 486 不同，本题不是"两端取"而是"**前缀取**"，且引入了一个**动态递增的参数 M**——本轮取 `X` 堆不仅获得本轮收益，还会通过 `M = max(M, X)` 扩大对手下一步的选择范围。这是一个"双重影响"决策，必须用带参博弈 DP。

**核心思想：博弈 DP（状态 (i, M)）**

- **状态结构变化**：486 是两端取 → 剩余是任意子区间 `[l, r]`，状态二维区间；1140 是前缀取 → 剩余永远是**后缀** `[i, n)`，位置用一维下标 `i` 即可描述，但新增了维度 **M**。

- **状态定义**：`dp[i][M]` = 从第 `i` 堆开始、当前参数为 `M` 时，当前玩家相对对手的**净优势**（己方得分 − 对方得分）。

- **转移方程**（核心，零和博弈）：
  ```
  dp[i][M] = max over X in [1, min(2M, n-i)]  ( 本轮收益 − 对手后续净优势 )
  ```
  - 本轮收益 = 取 `piles[i..i+X-1]` 的总和 = `suffix[i] − suffix[i+X]`（后缀和 O(1) 求）
  - 对手从 `i+X` 开始，参数变为 `max(M, X)`，其净优势 = `dp[i+X][max(M, X)]`
  - 因为是零和，对手的净优势就是我的劣势，所以用**减法**

- **边界**：`i == n` 时无石子可拿，`dp[n][*] = 0`。

- **填表方向**：`dp[i][M]` 依赖 `dp[i+X][...]`（`i+X > i`），故 **i 从大到小**倒序填；同一行内不同 M 之间互不依赖（都只依赖更大的 i 对应的行），顺序无关。

- **初始答案**：初始 `M = 1`，净优势 = `dp[0][1]`。

**返回值换算**：dp 存的是净优势，题目要的是 Alice 得分。由 `Alice + Bob = suffix[0]` 和 `Alice − Bob = dp[0][1]` 联立：

```
Alice = (suffix[0] + dp[0][1]) / 2
```

## 2. 代码实现

```java
package leetCode.moderately;

/**
 * @description: 1140. 石子游戏 II
 *
 * 【题目】若干堆石子排成一行，Alice 先手，两人轮流从前端取 1~2M 堆，取后 M = max(M, 本次取堆数)，初始 M=1。
 *         取完全部堆后，总石子数多者胜。求 Alice 最多能拿到多少颗石子。
 *
 * 【思路】零和博弈（博弈DP）
 *  1. 前缀取 → 剩余永远是后缀，状态用"当前起始下标 i"即可描述位置；
 *     且 M 会随每次取值动态增大，因此状态为二维 (i, M)。
 *  2. dp[i][M] 定义：从第 i 堆开始、当前参数为 M 时，当前玩家相对对手的净优势（己方得分 - 对方得分）。
 *  3. 转移：当前取 X 堆（1 ≤ X ≤ min(2M, n-i)），本轮收益 = suffixSum[i] - suffixSum[i+X]，
 *     对手在剩余后缀 [i+X, n) 上净优势 = dp[i+X][max(M,X)]，
 *     故 dp[i][M] = max over X ( 本轮收益 - 对手净优势 )。
 *  4. 边界：i == n 时无石子可取，dp[n][*] = 0（数组默认值）。
 *  5. 填表方向：dp[i][M] 依赖 i+X > i 的子问题，故 i 从大到小倒序填；
 *     同一行内不同 M 互不依赖，顺序无关。初始 M=1，净优势即 dp[0][1]。
 *
 * 【返回值换算】dp 存的是净优势，题目要的是 Alice 得分。
 *     Alice + Bob = suffixSum[0]，Alice - Bob = dp[0][1]，
 *     联立得 Alice = (suffixSum[0] + dp[0][1]) / 2。
 *
 * 【复杂度】时间 O(n³)，空间 O(n²)
 */
public class stoneGameII {
    /**
     * 零和博弈（动态规划-博弈DP）
     */
    public int stoneGameII(int[] piles) {
        int n = piles.length;
        // 后缀和：suffixSum[i] = piles[i..n-1] 的总和，suffixSum[n] = 0，O(1) 求任意区间和
        int[] suffixSum = new int[n + 1];
        for (int i = n - 1; i >= 0; i--) {
            suffixSum[i] = suffixSum[i + 1] + piles[i];
        }
        // dp[i][M]：从 i 开始、当前参数 M 下当前玩家的净优势
        int[][] dp = new int[n + 1][n + 1];
        // 填表（i 从大到小，保证依赖的 dp[i+X][...] 已算好）
        for (int i = n - 1; i >= 0; i--) {
            // 把 M 从 1 到 n 全部填一遍，这样未来任何 max(M,X) 都能直接查表
            for (int M = 1; M <= n; M++) {
                int best = Integer.MIN_VALUE;
                // X 从 1 取到 min(2M, n-i)：不能超过剩余堆数
                for (int X = 1; X <= 2 * M && i + X <= n; X++) {
                    // 本轮收益 - 对手在剩余后缀上的净优势
                    int cur = (suffixSum[i] - suffixSum[i + X]) - dp[i + X][Math.max(M, X)];
                    best = Math.max(cur, best);
                }
                dp[i][M] = best;
            }
        }
        // 净优势转 Alice 得分：Alice = (总和 + 净优势) / 2
        return (suffixSum[0] + dp[0][1]) / 2;
    }
}
```

## 3. 踩坑记录

- **算完 best 忘记赋值**：内层循环算出 `best` 后，若漏写 `dp[i][M] = best`，整个 dp 表保持默认值 0，返回恒为 0。这是最隐蔽的致命 bug——代码能编译、逻辑"看起来对"，但答案全错。
- **区间和求法的越界陷阱**：若用前缀和（长度 `n`），当 `i + X == n`（一把取到末尾）时 `prefixSum[i+X]` 越界。改用**后缀和**（长度 `n + 1`，`suffix[n] = 0`）即可自然处理边界，且 `X` 上限直接写 `i + X <= n`。
- **返回值定义与题目不一致**：dp 存的是**净优势**，题目问的是 **Alice 的最大石子数**。若直接返回 `dp[0][1]`，答案整体偏差。需要 `(总和 + 净优势) / 2` 换算。
- **X 的上限不是 `n-1` 而是 `n-i`**：从位置 `i` 开始最多只剩 `n-i` 堆，超出会越界。

## 4. 技巧总结

- **动态递增参数 M**：博弈中某次行动可能修改一个全局参数（`M = max(M, X)`），此时把该参数也作为状态维度即可，转移思想不变。DP 表越大越"空间换时间"——任何 `(i, M)` 直接查表。
- **"每个 i 都维护整行 M"**：因为未来任何一次 `max(M, X)` 都可能把 M 更新到任意值，所以 `i` 行内把所有 M 都算出来，避免运行时缺失状态。
- **状态维度由"动作形态"决定**：两端取 → 区间 `(l, r)`；前缀取 → 下标 `i` + 动态参 `M`。先想清楚"剩余局面长什么样"再定状态。
- 与 [877 石子游戏](石子游戏[877].md) 对比：877 因偶数堆+奇数总数约束可 O(1) 奇偶分组；1140 无该约束，必须完整博弈 DP。
- 相关经典解法：[博弈DP(零和博弈)](../经典解法/03-动态规划/博弈DP(零和博弈).md) 中 5.3.1 有本系列对照。

## 5. 思考过程

本次学习基于与 agent 的对话完成，记录认知转变过程：

1. **最初直觉**：一眼看出本题必须 DP——因为 M 动态递增，"取越多，对手下一步能取越多"，双方互相影响，来回纠缠，无法用 877 那样的奇偶分组化简。
2. **与 486 的结构对比**：曾以为和 486 一样是区间 DP，但被引导意识到：486 是**两端取**（剩余 = 任意子区间），1140 是**前缀取**（剩余 = 后缀）。这是状态从 `(l, r)` 变成 `(i, M)` 的根本原因。
3. **补齐零和博弈基础**：对"零和""净优势""当前优势 = 本轮收益 − 对手后续优势"这些概念先做了系统复习（用 486 的小例子 `[3,5]`、`[1,2,3]` 手算体会），理解了 dp 存净优势而非得分的原因。
4. **状态维度的顿悟**：确认 `dp[i][M]` 后，又理解了"每个 i 都要维护整行 M=1..n"——因为 max(M,X) 可能跳到任意值，不能只算部分 M。
5. **填表方向的纠结**：M 会变大变小，一度担心 M 的填表顺序。想通关键点：`dp[i][M]` 依赖的是**更大的 i**（`i+X`），同一行内 M 互不依赖，所以只要 `i` 倒序即可，M 顺序无所谓。
6. **写代码的连环踩坑**：先漏了 `dp[i][M] = best` 赋值（全表恒 0）；又遇到前缀和越界（改用后缀和）；最后发现返回值是净优势而非 Alice 得分（用公式换算）。三个 bug 都是"定义与实现的错位"，也是这次最大的收获。
