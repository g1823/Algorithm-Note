# 732. 我的日程安排表 III

## 1. 解题思路

### 问题转换

每次 `book(start, end)` 添加一个日程（区间 `[start, end)`）后，返回当前所有日程中**任意时刻的最大重叠次数**（即最大并发数）。

核心：统计所有时间点上，覆盖该点的区间数量的最大值。

### 三种解法对比

| 解法 | 核心数据结构 | 每次复杂度 | 空间复杂度 |
|:----:|:-----------:|:----------:|:----------:|
| 差分 + TreeMap | TreeMap | O(N) | O(N) |
| 动态开点线段树 | Node 对象（指针） | O(log R) | O(N log R) |
| HashMap + 完全二叉树编号 | HashMap | O(log R) | O(N log R) |

---

### 解法一：差分 + TreeMap（扫描线）

每个区间 `[start, end)` 相当于在 `start` 处 +1（开始），`end` 处 -1（结束）。用 TreeMap 按 key 排序后，扫描累加即可得到每个时刻的并发数，取最大值。

- 优点：实现极简，思路直观
- 缺点：每次 book 需要遍历全部端点，O(N²) 整体

### 解法二：动态开点线段树（Node 对象）

值域 `[0, 10⁹]` 太大，无法预先建树。只按需创建节点（走过的路径才存在），节点用 left/right 指针连接。

- 节点存储：`count`（区间最大次数） + `lazy`（待下发值）
- 每次 `book` 为区间 `[start, end)` +1
- 完全覆盖时 `count++` + `lazy++`，不下发
- 部分覆盖时先 `pushDown` 将 lazy 传给子节点，再递归
- 回溯时 `count = max(left.count, right.count) + lazy`

### 解法三：HashMap + 完全二叉树编号（官方标答）

**结合了数组线段树和动态开点的优点：**

- 用完全二叉树的编号规则：`root = 1`，`left = 2*idx`，`right = 2*idx+1`
- **但不用数组，改用 HashMap**：`tree Map<Integer,Integer>` 存储 count，`lazy Map<Integer,Integer>` 存储懒标记
- 只有被访问到的 idx 才会出现在 Map 中

**其巧妙之处在于：**

1. **物理上无节点对象** —— 不需要定义 Node 类，天然适合函数式递归
2. **idx 隐式编码了父子关系** —— 无需 left/right 指针，通过 `2*idx` 和 `2*idx+1` 定位子节点，等价于数组线段树的隐式树结构
3. **HashMap 实现了动态扩容** —— 不浪费空间，只有被访问到的 idx 才占用 Map 条目
4. **lazy 不下发** —— 回溯时 `tree.put(idx, lazy.getOrDefault(idx,0) + max(left, right))`，无需物理下发，直接从 lazy Map 取值
5. **代码极简** —— 仅 10 行有效代码，却实现了一个支持区间更新的线段树

> 这种模式本质上就是用 **Map 模拟了动态数组**，同时利用了**完全二叉树的天然编号**，是"静态数组效率 + 动态节点灵活"的完美折中。

## 3. 踩坑记录

### 半开区间边界判断

写线段树时，区间 `[l, r)` 和更新区间 `[start, end)` 不重叠的条件是 `start >= r || end <= l`。

**错误写法**：`start > r || end < l`

当边界重合（如 `end == node.l` 时，区间无重叠但条件为 false），会导致无限递归创建子节点。

### 动态开点的 pushDown 时机

`pushDown` 中必须先创建子节点，再下发 lazy。写成：

```
if (node.lazy == 0) return;     // ❌ 子节点还没创建就不创建了
```

会导致后续递归 `update(node.left, ...)` 传入 null，引发 NPE。正确顺序：

```
// 1. 先确保子节点存在
if (node.left == null) node.left = new Node(...);
if (node.right == null) node.right = new Node(...);
// 2. 再下发 lazy
if (node.lazy == 0) return;
node.left.lazy += node.lazy;
...

```

| 线段树 ∣ 动态开点 | `经典解法/01-数据结构/线段树.md` | 动态创建节点，解决值域大且数据稀疏的问题 |
| 懒标记 (Lazy Propagation) | `经典解法/01-数据结构/线段树.md` | 区间更新时延迟下发，保证 O(log R) |

### solution4 的精妙之处 —— "虚拟动态开点"

官方标答用 HashMap + 完全二叉树编号实现动态开点线段树，值得单独提炼成**小技巧**：

```
用 Map 模拟数组，用 2*idx / 2*idx+1 隐式编码父子关系
```

这种模式适用于：
- 值域极大（如 10⁹）
- 操作次数适中（N ≤ 几百到几千）
- 需要线段树功能但不想写面向对象的 Node 结构

相比传统动态开点（Node left/right 指针）：
- 代码更短（省去 Node 类、pushDown 方法）
- 索引更直观（child = parent*2）
- 但 idx 可能膨胀到较大值（2^30 ≈ 10⁹），不过 HashMap 只存被访问的条目

## 5. 思考过程

### 关键思维转变：从"预先构造"到"动态创建"

之前做过的线段树题目（如 `SeparateSquares`、`CountSmaller`）都有一个共同前提：**所有数据在初始化时就能确定**。
- `CountSmaller`：离散化后得到值域数组，建树时就知道所有可能出现的下标
- `SeparateSquares`：虽然坐标值很大（10⁹），但可以通过二分或离散化转化为已知范围

所以之前的套路是：**先确定范围 → 建树（可以是数组或 Node[]）→ 再更新/查询**。

但在 732 中，调用 `book` 之前根本不知道会有哪些端点值，数据是**动态流入**的。无法用离散化（因为没有全集），也无法开 10⁹ 的数组。

这就必须切换思维模式：

> **从"先建好再用" → "边走边建，只建需要的路径"**

递归参数携带当前区间 `[l, r)`，遇到需要递归的节点时才 `new Node()`。未走过的路径根本不存在，这正是"动态开点"的核心。

### 区间切分方式：为什么按中点切，而不是按传入区间切

实现时曾出现过一个误区：在 `update` 中，尝试按**更新区间的边界**来切分子区间。

错误想法示例：

```
// ❌ 错误：按传入区间切分
if (start > l)  update(left,  l, start);   // 左段只到 start
if (end   < r)  update(right, end, r);     // 右段从 end 开始
```

这本质上是**区间树（Interval Tree）**的思路，不是线段树。问题是：
- 每个节点的边界不固定，切割依赖于更新区间，无法形成统一的树结构
- 对于多个重叠更新，每次的切分点不同，逻辑极难维护

**正确的做法**：无论更新区间是什么，节点始终按自己的中点切分：

```
int mid = l + (r - l) / 2;  // 只依赖当前节点自己的边界
if (start < mid) update(left,  l, mid, start, end);
if (end   > mid) update(right, mid, r,   start, end);
```

这样：
- 树的形状是**确定且可预测的**，不会随更新区间变化
- 每个节点的区间是固定的，天然支持分治
- 更新区间 `[start, end)` 无论落在哪，都能在 O(log R) 内定位到完全覆盖的节点
- 这也是线段树"平衡二叉树"性质的来源 —— 每次均匀二分，树高恒为 log(R)

> 线段树的本质是**对值域做固定的二分**，而不是对更新区间做切分。切分策略由树自己的结构决定，和数据无关。

### 两种动态开点风格的对比

写 solution2 时，我最初让每个 Node 存储自己的边界 l/r（冗余），且 pushDown 同时负责创建子节点和下放 lazy。和朋友讨论后发现：
- l/r 可通过递归参数传递，Node 不必存
- pushDown 应单一职责：只下放 lazy，子节点创建应在 update 中提前处理

后续看到官方标答，眼前一亮 —— 连 Node 类都不要了，直接用 HashMap + 二叉树编号。这实际上是把"数组式线段树"中数组的静态下标映射，换成了 HashMap 的动态存储，同时保留了完全二叉树编号的便利性。
